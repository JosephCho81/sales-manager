# 2026-05 AL30(현대제철) 감가 처리 — 검토 결과

작성 2026-07-30 · 구현 2026-07-31 · **모델 정정 2026-07-31** · 상태: **배포 완료 (마이그레이션 015 적용 완료)**

> **용어 주의** — "7월분 계산서"는 **납품월** 기준이고, AL30은 offset=2라 그 계산서의
> **지급월은 2026-09**다. 감가가 반영되는 계산서 = 화림 **7월분**, 실제 입금 적용 = **9/30**.
> 문서·화면 모두 계산서는 납품월, 지급일정 페이지는 지급월로 부른다.

> **남은 것** — 오늘(7/31) 현대 입금 기록 + 화림 5월분 전액 지급 입력.
> 9/30 지급 전에 화림 7월분 실계산서 부가세 대사(§9).

> **정정 이력** — 초판은 "실제 역발행 계산서 = 159,310,954, 입금만 61,797 부족"으로 보고
> *매출 계산서 불변 + `paid_amount`만 기록* 모델을 세웠다. 사용자 확인 결과 **실제 역발행
> 세금계산서 자체가 159,249,157**(현대가 감가를 통보 없이 반영해 발행, 우리가 감가 없이 승인·저장).
> 따라서 매출 계산서도 감액되어야 하고, 커미션 3사 배분도 그만큼 줄어든다. 아래는 정정된 모델.

## 1. 무슨 일이 있었나

현대제철이 **통보 없이** 5월 납품분 감가를 반영해 역발행했다. 역발행은 월 3회(10일 단위)이고
감가 안내가 따로 없어 우리는 **감가 없는 금액으로 저장**했다. 60일 뒤 7/31 입금액을 보고 알았다.

### 대사 결과 (실 DB 조회로 확인)

| 항목 | 금액 |
|---|---|
| 우리 시스템 저장액 (5월 납품분, 지급월 2026-07) | 공급가 144,828,140 / VAT 14,482,814 / **총 159,310,954** |
| **실제 역발행 계산서 = 7/31 실입금** | **159,249,157** |
| 차액 | **61,797 = 감가 56,179 + VAT 5,618(반올림)** |

숫자 정확히 일치. 감가 공급가 56,179원, 부가세 별도.
**틀린 쪽은 우리 저장액이다** — 계산서를 실제 발행액으로 맞춰야 한다.

### 회수 방식 (화림 합의)

- 7월 지급분(5월 납품): 화림에 계산서대로 **전액 지급**
- 8월 지급분(6월 납품): **전액 지급** (감가 반영 없음)
- **7월 납품분 계산서에 감가 반영** → AL30 offset=2 이므로 **9/30 지급분에서 회수**
- 계산서는 **공급가에서 56,179를 뺀 금액으로 발행**, 감가 금액은 부가세 포함 그대로 화림에 반영 (총 −61,797)

→ 7/31 ~ 9/30 두 달간 **61,797원 자금 선지급**.

## 2. 확정 타임라인 (감가 1건 = 4개 시점)

|---|---|---|---|
| 7/31 | 현대 → 한국에이원 (5월분) | **159,249,157** (감가 반영 발행) | 실입금액 입력 → 차액 61,797이 감가로 확정, 계산서 재생성 |
| 7/31 | 한국에이원 → 화림 (5월분) | 131,961,434 | **전액 지급. 차감 금지** |

| 9/30 | 한국에이원 → 화림 (7월분) | 계산서가 **이미 −56,179 발행** | 그대로 지급 → **회수 완료** |

### 커미션 (3사 배분)

커미션은 **그달 실제 계산서 기준 마진(매출 − 매입)의 1/3**이라는 원칙을 유지한다.
매출이 줄면 마진이 줄고, 회수월에 매입이 줄면 마진이 늘어난다 → 3사가 함께 부담하고 함께 회수.

| 지급월 | 마진 | 금화 / 나성 |
|---|---|---|
| 2026-07 (5월분) | 144,771,961 − 119,964,940 = **24,807,021** | 각 공급가 8,269,007 / **총 9,095,908** |
| (감가 없었다면) | 24,863,200 | 각 9,116,506 · 9,116,507 |
| 2026-09 (7월분) | 회수분 **+56,179** | 각 **+약 18,726** |

→ 두 달 합산하면 원상복구. 1/3 나머지 처리 때문에 **최대 1원** 어긋날 수 있다(금액 소멸 아님).

## 3. 계산서 생성 규칙

**① 7월 지급월 — 5월 납품 현대 매출 (감액 발행)**

```
공급가 = 144,828,140 − 56,179 = 144,771,961
VAT    = 14,482,814 − 5,618   = 14,477,196   ← 일괄 재계산 금지
총액   = 159,249,157                          ← 실제 역발행·입금액과 1원까지 일치
```

역발행이 월 3장일 때는 **마지막 발행 구간 1장에만** 반영한다(분산하면 라인별 VAT가 어긋난다).

**② 화림 7월분 매입 계산서 (회수) — 지급월 2026-09**

```
공급가 = 7월 총액 − 56,179
VAT    = (원래 VAT) − 5,618      ← 일괄 재계산 금지
총액   = −61,797                 ← 현대 감액분과 1원까지 상계
```

⚠️ **1원 리스크**: 차감된 공급가에 일괄 10%를 다시 계산하면 5,617이 나올 수 있다(56,179×0.1 = 5,617.9).
동창 케이스와 동일한 문제 → **`vatOverride`로 "원래 VAT − 5,618" 고정**이 맞다. 화림 7월분 실계산서로 최종 대사(지급은 9/30).

## 4. 담당자 혼동 방지 — 핵심 검토

혼동의 원인은 금액이 아니라 **구조**다. 감가 1건이 3개월에 걸쳐 4개 사건을 만드는데
각각 다른 월 페이지에 흩어져 있고, **그중 2건은 "아무것도 하지 않는 것"이 정답**이다.
사람은 "하지 말아야 할 일"을 기억하지 못한다.

### 예상 실수 4가지

| # | 실수 | 결과 |
|---|---|---|
| 1 | 7/31 입금액이 다르니 매출 금액만 손으로 고쳐놓음 | 감가 기록이 안 남아 **9월 회수분이 영영 안 잡힘**. 커미션도 총액 기준으로 과지급 |
| 2 | 7/31 그냥 "지급완료" 체크 | 61,797 흔적 없이 소멸. 9월 회수 사실을 아무도 모름 |
| 3 | 8/31 화림 지급 시 "감가 났으니 빼야지" 하고 차감 | **이중 차감** — 과소지급 후 9월에 또 차감 |
| 4 | 9/30 화림 계산서가 총액과 안 맞음 → "생성 오류" 판단하고 재생성 | 감가 반영분 소실. **회수 실패** |

3·4번이 특히 위험. 현재 설계(계산서 memo 한 줄)로는 넷 다 못 막는다.

### 방지 설계

원칙: **담당자에게 계산을 시키지 말 것.** 각 화면에서 "이번 달 이 건은 어떻게 하라"를 명시하고,
특히 **아무 일도 없어야 하는 달에 "차감 없음"을 적극적으로 표시**한다.

**① 실입금액 입력 강제 (7/31 — 실수 1·2 차단)**

지급완료 체크를 금액 입력형으로 교체. 기본값은 계산서 총액, 다르게 입력하면 사유 선택 필수.

```
[지급완료 처리]  현대제철 → 한국에이원 (5월분)
  계산서 총액   159,310,954
  실입금액      [159,249,157]        ← 차액 61,797 감지
  ⚠ 차액 사유가 필요합니다
  ( ) 감가 — 회수처 [화림 ▾] 회수 납품월 [2026-07 ▾]
  ( ) 이체수수료  ( ) 기타 [           ]
```

사유 선택 시 감가 레코드 자동 생성. 계산서 금액은 **읽기 전용으로 잠금**(수정 시도 자체 차단).

**② 계산서 행 자동 배지 (8·9월 — 실수 3·4 차단)**

- 8월 화림 행 → 🔒 `감가 차감 없음 — 5월 감가는 9월분에서 회수 예정` (회색)
- 화림 7월분 행(2026-09 지급월) → ✅ `5월 감가 회수 −56,179 (VAT −5,618) 반영 발행` (파랑)

**"차감 없음" 배지가 이 설계의 핵심.** 조용히 있으면 담당자가 스스로 판단하려 들고 그게 실수 3이다.

**③ 상단 미회수 배너 (전 기간)**

```
미회수 감가  61,797원  — 2026-05 AL30(현대) / 화림 2026-07분에서 회수 예정 (9/30)
```

잔액 0이면 자동 소멸. 어느 달을 보든 눈에 들어와 "잊어버림"이 구조적으로 불가능해진다.

**④ 용어 분리 (누적 혼동 차단)**

현재 "감가"가 두 가지를 가리켜 이미 위험:

| | 분탄 | AL30 |
|---|---|---|
| 유형 | **보관형** | **통과형** |
| 동작 | 매입(동창)만 차감 | 입금 감소 → 화림에서 회수 |
| 최종 | 통장에 남음, 계약종료 후 렘코 반환 | 잔액 0 |

패널 라벨을 `감가(보관 — 렘코 반환)` / `감가(회수 — 화림)`로 분리해야
담당자가 둘을 같은 규칙으로 처리하는 사고를 막는다.

## 8-1. 커미션 부가세 1원 수정 (2026-08-03)

지급월 2026-07 화면에서 금화·나성 커미션 VAT가 **516,111**로 나왔으나 실제 계산서는 **516,110**.

```
마진 15,539,500 → 1/3 = 5,179,833(금화) / 5,179,834(나성)
감가 56,179 분담 후 각 공급가 5,161,107
  일괄 10%      : 516,110.7 → 516,111   ✗
  라인별(정답)  : 517,983 − 1,873 = 516,110   ✓   (감가 1/3분 18,726·18,727의 VAT를 따로 뺌)
```

매출(현대)·매입(화림) 계산서에 이미 적용돼 있던 **라인별 VAT 원칙이 커미션에만 빠져 있었다.**
`al30.ts`에 감가 반영 전 배분액(`baseGeumhwa`/`baseRaseong`)을 누적해 `commVat()`으로 `vatOverride` 지정.
회수월(+감가)도 같은 식으로 `calcVat(base) + calcVat(회수분)`. 감가 없는 달은 기존 일괄 10% 유지.

→ **적용하려면 지급월 2026-07 계산서 재생성 필요** (지급완료·실입금액은 재생성 시 보존됨).
